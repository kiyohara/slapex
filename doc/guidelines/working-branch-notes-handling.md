# Working Branch Notes 取り扱いガイドライン

この文書は、`working-branch-notes/` 配下の note の性質、整合性スコープ、ライフサイクル、メンテコスト判断を定義する共通正本である。

`working-branch-notes/**/*.md` の禁則(秘密情報・個人情報・顧客固有情報など)は `doc/guidelines/working-branch-notes-security.md` を正本とする。本ガイドラインは、その手前の「note をそもそもどう扱うか」を扱う。

## 性質

- note は **ブランチ単位の作業目的、状況、判断、引き継ぎメモ** である。
- 最終仕様書ではない。最終実装を網羅的に記述したり、実装と 1:1 に保つことを目的としない。
- 主に AI agent と共同作業するときに、複数セッションをまたいで共有したい文脈を残す用途を想定する。

## 整合性のスコープ

- 当ブランチの作業判断 / 経緯を読める範囲で十分。
- 最終実装との 1:1 整合や、note 内の異なる記述同士の細かな整合は要求しない。
- 振り返り時に作業の流れと判断理由が辿れれば、note としての役割は果たしている。

## ライフサイクル

- note は通常のリポジトリファイルとして扱い、対象 PR に含める。
- 該当 PR の merge 後、note は別途 cleanup PR で整理対象となる。
- 長期保守は前提にしない。長期的に残したい情報は `doc/guidelines/` 配下の正本へ移す。
- cleanup の閾値、頻度、詳細な運用ルールは、実際の蓄積状況を見て後から決める。

## メンテコスト判断

- note 内の stale 表現指摘は **ローコストで直せるなら直す**。
- 修正に相応のコストがかかる場合は **据え置きを許容する**。
- レビューでは note 内の細かな整合性指摘は避けるか、`[fyi]` レベルにとどめる(最終仕様書ではないため)。
- メンテコストが本ルールの趣旨を超え始めたら、cleanup PR で一括整理するか、内容を `doc/guidelines/` 配下の正本へ昇格させる選択肢を取る。

## ファイル名

PR 採番前は `draft_<escaped-branch-name>.md` とする。

```text
draft_test-github-actions-new-runner.md
```

PR 採番後は `<PR-number>_<escaped-branch-name>.md` とする。

```text
2895_test-github-actions-new-runner.md
```

PR を開いた後は、必要に応じて `git mv` で `draft_...` から `<PR-number>_...` へリネームする。

原則は 1 ブランチ 1 note とし、同じファイルに追記する。補助 note を分けたい場合は、主 note の basename に suffix を付ける。

```text
draft_test-github-actions-new-runner__agent-review.md
2895_test-github-actions-new-runner__part2.md
```

### ブランチ名の escape

ファイル名に使うブランチ名は、次のように変換する。

- `/`, `:`, `\`, `*`, `?`, `"`, `<`, `>`, `|` は `-` に置換する。
- 空白、制御文字、環境によってファイル名として扱いにくい文字も必要に応じて `-` に置換する。
- 連続する `-` は 1 つにまとめてよい。
- 先頭と末尾の `-` は削除してよい。
- 変換後に空になった場合は `branch` を使う。

### note の探し方

- PR 番号が分かる場合は `<PR-number>_<escaped-branch-name>.md` を優先する。
- PR 番号が分からない場合は `draft_<escaped-branch-name>.md` を見る。
- `draft_...` と `<PR-number>_...` の両方がある場合は、番号付き note を正とし、`draft_...` は移行漏れとして扱う。

## 推奨構造

新しい note を作る場合は、`working-branch-notes/_template.md` をコピーして使うことを推奨する。

```md
# 作業ブランチメモ

- ブランチ:
- PR:
- 最終更新:

## 目的

## 現在の状況

## 決定事項

## 次にやること

## 検証

## リスク・ブロッカー

## セッションログ
```

最新の目的、状況、次の作業は上部の各セクションに集約し、細かい経緯は `セッションログ` に短く追記する。

## 書くとよいこと

- このブランチで達成したい目的
- 現在の作業状況
- 重要な判断とその理由
- 次にやること
- 実行した検証と結果
- 未解決のリスク、ブロッカー、注意点
- セッションをまたいで AI agent や人間に引き継ぎたい文脈

## 書かないこと

情報統制の禁則は `doc/guidelines/working-branch-notes-security.md` を正本とする。値の例示が必要な場合は、ダミー値、プレースホルダ、変数名だけを使う。
